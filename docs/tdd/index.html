01How to read this design

This document is the technical design for running NAMAA as a national operating platform. It is the reference for platform, security, and product engineering. An API specification and a Crossplane composition catalog follow from it; they are not duplicated here.

The word CKE in the deployment brief is the Kubernetes engine that runs the workloads. On Google Cloud that engine is Google Kubernetes Engine (GKE). Every CKE cluster in this design is a private regional GKE cluster in Dammam. If CKE was meant as a different distribution, the landing zone, GitOps flow, and security planes still hold; the cluster claim in Crossplane is the piece that would change.

Residency rule. Agronomic data, operator identities, session recordings, backups, and LGTM telemetry are stored only in me-central2. Organization policy restricts resource locations to that region. Egress that would ship logs or traces to a SaaS observability region is denied.

02A farm unit

The unit is the thing the platform operates. Everything else — clusters, topics, dashboards — exists to sense this unit, decide, and act on it. One unit is 20 hectares and a 1.2 MW agrivoltaic block. Crops sit under and between the trackers. A controlled-environment module grows high-value organics. Sub-surface drip is powered by the block, with a battery so pumps ride through cloud.

The gateway keeps the last approved irrigation schedule, tracker plan, and battery policy, and it keeps executing them when the wide-area link is down. Desert links fail. A cloud round-trip is not allowed to be required for a pump that is already inside an approved envelope. New setpoints wait for the link. Acknowledgements and fresh samples catch up when it returns.

Crop groups in the prototype — dates, forage, vegetables, pilots — become irrigation zones. CEA modules are a separate controlled volume on the same unit power and network, with their own EC, pH, temperature, and humidity.

03System context

People use the console. Gateways speak MQTT. Forecasts come from the National Center for Meteorology through an adapter. Privileged engineers do not get standing cluster credentials; they come in through Teleport. Detection and intelligence sit beside the product, not in the irrigation path.

05Control loop

Recommendations in the prototype are three kinds: shift drip into the night, change tracker tilt, and pre-charge a battery ahead of cloud. Production keeps those kinds. A recommendation is a record with a type, a confidence, an impact line, and a state. It is not an immediate write to a valve.

5.1 Envelope

Each zone has an envelope an administrator sets: maximum minutes of drip per night, earliest and latest start, maximum tilt change in degrees, maximum battery charge rate. A recommendation whose setpoint sits inside the envelope and whose confidence is at least 85 is applied and recorded. Anything outside is queued on the IoT & AI screen. Rejected recommendations stay in the audit table. The prototype’s sample recommendations (night irrigation on units 12–18, +6° west tilt after 14:30, pre-charge before 11:20) are the acceptance tests for this loop.

5.2 Recommender v1

Version 1 is deterministic and inspectable, running on the CKE cluster. It does not call a model API outside the Kingdom.

  • Irrigation. Soil-moisture slope plus the NCM temperature forecast. If moisture is falling and the day-peak forecast is above the crop threshold, propose a night shift of the pending drip volume.
  • Shading. Inter-row irradiance above the crop stress threshold in the afternoon proposes a westward tilt change, rejected automatically if the estimated energy loss exceeds 2%.
  • Energy. A forecast cloud band proposes pre-charge so the pump interval stays off the grid import.

A later model can replace a rule behind the same recommendation record. Training data is the in-region archive. Serving stays on the CKE cluster so a regional gap in a hosted ML product does not block actuation.

06Domain data

Operational state lives in Cloud SQL for PostgreSQL with the Timescale extension, private IP, regional high availability, customer-managed encryption in Cloud KMS in me-central2. Point-in-time recovery is 7 days. Daily backups are kept 30 days in the same region.

Unit status moves only forward: prep → prepared → active. Active is what counts toward the 214-of-500 style fleet total and toward megawatts online. A unit that is not active does not receive actuation commands.

Personal data is the operator account: name, email, role, region scope. It stays in Cloud SQL. Gateway payloads are agronomic, not personal. Cyfirma receives no agronomic data and no operator profile. The MDR service, once a vendor is selected, receives security events; the user identifier on those events is the account id, not the name, unless an investigation ticket asks for more.

6.1 Sizing

Ten thousand sensors at one sample per 30 seconds is about 30 million samples a day. That is a small Timescale workload. The cluster is sized for headroom and for zone failure, not for a stream-processing platform. Ingest is horizontally scaled on CPU. The broker is a 3-pod EMQX cluster with a pod anti-affinity across zones.

07Google Cloud landing zone

The platform runs in Google Cloud region me-central2 (Dammam), three zones. Google Cloud documents this region as inside the Kingdom, reached for KSA billing through the reseller CNTXT, and assessed by the National Cybersecurity Authority against the Essential Cybersecurity Controls and the Cloud Cybersecurity Controls. This design uses that region so residency is a location constraint, not a promise in a diagram.

Resource-location organization policy allows only me-central2. Crossplane compositions refuse a claim that asks for any other region on a data-bearing resource. Backups and replicas follow the same constraint. There is no multi-region bucket.

7.1 Network

  • Private GKE control planes. kubectl and database sessions enter through the Teleport agents, which already sit on the VPC.
  • Nodes have no public IPs. Egress is Cloud NAT, with an allow-list: NCM adapter destinations, Cyfirma API, the chosen MDR ingestion endpoint, OS package mirrors, and nothing else of consequence. Grafana Cloud and other telemetry SaaS endpoints are explicitly denied.
  • Cloud SQL and Memorystore have private IP only.
  • Public entry is one HTTPS load balancer in front of the console and the BFF, with Cloud Armor. The MQTT listener is a separate TCP load balancer, mutual TLS, device certificates issued per gateway. It is not on the public web path.
  • Map tiles are served from the console origin. Leaflet does not point at a public OpenStreetMap host, because that would export viewport locations.

7.2 Encryption and keys

Cloud KMS in namaa-sec, with Cloud HSM keys for Cloud SQL, GCS, and the disk encryption of the CKE node pools. Applications do not handle key material. Workload Identity binds each Kubernetes service account to a Google service account that can do one job: ingest can subscribe and write objects, reporting can write report objects, External Secrets can read a named set of secrets, Crossplane’s provider identity lives only on the management cluster.

08CKE workload clusters

Each CKE cluster is a regional GKE Standard cluster across me-central2-a, b, and c. Standard, rather than Autopilot, because the broker, the Timescale-adjacent pools, the Teleport agent, and a later inference pool need node-pool control. Release channel is regular. Workload Identity is on. Binary Authorization is on: only images signed by the CI key in Artifact Registry may run in production.

Edge behaviour during a platform outage: gateways continue the last acknowledged schedule. They buffer samples on disk (at least 72 hours) and replay them. They do not invent new setpoints.

09Crossplane

Infrastructure is claims in Git. Crossplane on the management cluster is the only identity that can create Google Cloud resources for NAMAA. People do not click projects into existence, and CI does not hold a project-owner key.

Providers: provider-gcp (family: compute, container, sql, storage, pubsub, dns, kms, secretmanager), provider-kubernetes for namespaced add-ons that must exist before Argo CD’s app waves, and the Helm provider only where a vendor chart is the upstream install (EMQX operator, Teleport). Application manifests are not Helm-from-Crossplane; Argo CD owns those.

10Argo CD

Git is the desired state of both cloud resources and workloads. Argo CD runs on the management cluster and is the only deployer into the CKE workload clusters. Sync to production is manual. Sync to dev is automated on the dev branch.

10.1 Repositories and promotion

CI builds on merge to the service repository, pushes to Artifact Registry in me-central2, and signs the image. A bot opens a pull request in namaa-gitops that changes only the digest for dev. Promotion to staging is a pull request that copies that digest. Promotion to prod is a release pull request with two reviews, one of them from the platform owner. Argo CD’s prod project has sync windows that exclude Fridays and public holidays unless an incident override is recorded in the change ticket.

Argo CD projects are infra, addons, and namaa. The namaa project can only deploy into the application namespaces. It cannot create ClusterRole or anything in kube-system. Infra drift on a Crossplane claim pages the platform on-call; application drift auto-heals in dev and pages in prod without auto-heal, so a hotfix on a node is visible.

Source repositories may be hosted outside the Kingdom. They hold no samples, no credentials, and no session recordings. If a later policy requires the Git host itself to be in the Kingdom, the same three repos move without a design change. That hosting choice is open (section 16).

11LGTM, hosted in the Kingdom

Observability is the Grafana LGTM stack running on its own CKE cluster in namaa-obs, in Dammam. Loki stores logs, Grafana is the console, Tempo stores traces, Mimir stores metrics. Blocks and index live on GCS buckets in me-central2. This is not Grafana Cloud. Collectors do not remote-write to an endpoint outside the Kingdom, and the NAT allow-list makes that path fail closed.

11.1 What is collected

  • Metrics. Golden signals per service (rate, errors, duration), broker depth, ingest lag, command lag, recommendation cycle time, node and pod saturation, certificate expiry.
  • Logs. Application logs as structured JSON with trace id, unit id where the request is about a unit, and no sensor payload. Audit logs from Cloud Audit, GKE audit, Argo CD, and Teleport.
  • Traces. BFF to domain service to database. Command path from approval to MQTT publish. Ingest path from broker to commit.

Alerts that page a human: ingest lag above 30 seconds for 10 minutes, command error budget burn, broker under-replicated, Cloud SQL failover, Argo CD prod out of sync, Teleport auth down, a denied location in a Crossplane event, Binary Authorization rejection in prod. Alert notifications stay on an in-Kingdom channel. The alert text carries identifiers, not sample values.

12Teleport

Teleport is the privileged-access system. It is the way a human reaches a CKE API, a Cloud SQL session, an Argo CD admin screen, a Grafana admin screen, or a break-glass shell. Standing kubeconfigs are not issued. Certificates are short-lived. Every session is recorded, and the recording is stored on the management cluster’s in-region disk and bucket.

Each CKE cluster runs a Teleport Kubernetes agent. Cloud SQL is registered through the database agent in namaa-prod and namaa-nonprod; there is no direct authorized network from a laptop. Device trust is required for prod roles. The corporate IdP is the only SSO source. Local Teleport users are limited to the break-glass pair, stored offline.

Join to a new cluster is part of the XCkeCluster composition: the agent token is written to Secret Manager and picked up by External Secrets. A cluster without a healthy agent fails its Crossplane readiness check.

13Cyfirma and managed detection

Cyfirma is the threat-intelligence source. Managed detection and response is a required capability, and the product that provides it has not been chosen. This section specifies the interface that vendor must meet. Neither capability sits on the path from a moisture sample to a valve. Both sit on the security plane, fed from namaa-sec, with copies of evidence still in LGTM. No security copy leaves the Kingdom until that vendor is selected and decision D4 is closed.

13.1 Cyfirma

A connector workload in namaa-sec pulls indicators and intelligence items from the Cyfirma API on a fixed schedule and on demand during an incident. Pulled items are stored in a bucket and a table in the Kingdom. Three uses are in scope:

  • Edge blocking. Network indicators that match the console’s exposure are compiled into a Cloud Armor address list. The list is reviewed by security before it is enforced, except for indicators Cyfirma marks as active exploitation against our own domains, which enforce immediately and page.
  • Vulnerability context. Image and Kubernetes advisories are joined to the Artifact Registry inventory so a digest already pinned in Git can be flagged for a promotion freeze.
  • Brand and domain. Lookalike domains and leaked operator mailboxes are tickets, not automatic controls.

The connector’s credential is in Secret Manager, accessed through Workload Identity. Agronomic databases are not granted to that identity.

13.2 Managed detection and response

The MDR vendor will be selected later. Until that choice is made, the design names the capability, not a product. The chosen service watches the security stream, escalates findings, and recommends containment. NAMAA still executes containment, because the credentials that can change production sit with Teleport and Crossplane, not with the MDR tenant.

The export is a filtered copy of the security stream in section 13’s diagram. It is shipped from namaa-sec by a dedicated forwarder, and that forwarder is not deployed until the vendor and the residency terms in D4 are agreed. Delivery failures alert in LGTM; they do not block ingest or irrigation. Findings come back as tickets into the same incident channel the SRE on-call already uses. A finding that names a unit gateway is treated as a device incident: revoke that device certificate, leave the last schedule running, and replace the gateway credential before the unit is allowed to reconnect.

14.1 Device identity

Each gateway has a certificate whose common name is the unit id. The broker rejects a publish or a subscribe whose topic unit id does not match the certificate. Certificates are issued by a private CA in namaa-sec (Certificate Authority Service in me-central2). Rotation is yearly, or immediately on an MDR finding or an operator incident. A revoked certificate cannot drain the command topic of another unit.

14.2 Software supply

Production nodes run only images that Binary Authorization can tie to the CI signer and to a digest that namaa-gitops has merged. Base images are pinned. The console’s dependency install happens in CI, not on a laptop upload. Crossplane provider packages are pinned by digest in namaa-compositions the same way.

15Environments and operations

15.1 Acceptance of a release

Staging runs the three prototype scenarios against synthetic gateways before a prod sync is offered:

  1. Moisture falling and a high temperature forecast produces an irrigation recommendation. Inside the envelope it dispatches; the synthetic flow meter verifies it.
  2. Afternoon irradiance above the stress threshold produces a tilt recommendation that is refused when the energy-loss estimate is over 2%.
  3. A forecast cloud band produces a battery pre-charge that the synthetic inverter acknowledges.

A fourth check pulls the console off the gateway: with the broker partition for that unit black-holed, the gateway keeps the previous schedule and replays buffered samples when the partition returns.

15.3 Rebuild

A lost workload cluster is recreated by reconciling the XCkeCluster claim and letting Argo CD sync. Cloud SQL is restored from PITR into the same region. Gateways, which have been executing the last schedule, reconnect, replay samples, and receive any commands that were not acknowledged. A lost observability cluster is rebuilt the same way; it does not block irrigation. A lost management cluster is the painful one: compositions and Argo CD are reinstalled from namaa-compositions, Teleport authority is restored from its in-region backup, and no application deploy happens until Teleport session recording is healthy again.

17Build order

The order is the dependency order. A later step is not useful without the earlier one.

  1. Landing zone. Organization policy, Shared VPC, KMS, projects, Teleport, Argo CD, Crossplane compositions. Prove a private CKE cluster comes up from a claim and is reachable only through Teleport.
  2. LGTM. Observability cluster, Alloy on the management cluster, retention buckets, paging. No workload is deployed “temporarily without logs”.
  3. Data plane. Cloud SQL, Redis, Pub/Sub, GCS, External Secrets. Device CA.
  4. Edge path. EMQX, ingest, one synthetic gateway, samples visible in the console map.
  5. Control path. Recommender v1, envelopes, command, verification. The three acceptance scenarios.
  6. Domain screens. Land, irrigation, CEA, energy, economics, benchmarks, goals, report packs written to GCS.
  7. Security integrations. Cyfirma connector, and the MDR forwarder after a vendor is chosen and D3 and D4 are closed. Cloud Armor fed by indicators.
  8. Pilot hub. One regional hub on real gateways, actuation inside envelopes, then the rest of the hubs.
